# ISO/IEC/IEEE 29148 — Requirements Engineering

## 1. Purpose

Document how ISO/IEC/IEEE 29148 is used as a requirements engineering
reference within Ptilon.

This document provides a Ptilon interpretation and does not reproduce the
standard.

---

## 2. Reference

**ISO/IEC/IEEE 29148 — Systems and software engineering — Requirements
engineering**

Official reference: <https://www.iso.org/standard/72089.html>

The applicable edition should be explicitly identified when a project has
contractual, regulatory, or formal conformance requirements.

---

## 3. Role in Ptilon

ISO/IEC/IEEE 29148 provides the primary requirements engineering foundation for
Ptilon.

Ptilon uses it to structure the transition from business or user intent into
clear, verifiable, and traceable requirements.

This is particularly important in AI-assisted development because AI can
generate plausible requirements that contain ambiguity, unsupported
assumptions, omissions, or contradictions.

---

## 4. Requirements engineering principles

Ptilon treats requirements as controlled engineering artifacts.

Requirements should be:

- necessary;
- appropriate to their level;
- unambiguous;
- complete within their intended scope;
- consistent;
- feasible;
- verifiable;
- traceable;
- prioritized;
- uniquely identifiable when appropriate.

The appropriate degree of rigor depends on project context and risk.

---

## 5. Requirement levels

Ptilon distinguishes, when applicable, between different levels of
requirements.

Examples include:

- stakeholder or business needs;
- system requirements;
- software requirements;
- functional requirements;
- quality requirements;
- constraints;
- security requirements;
- regulatory requirements.

The project should define the terminology and hierarchy appropriate to its
context.

---

## 6. From intent to specification

Ptilon structures requirements development as a controlled progression:

Intent → Requirements → Specification → Acceptance Criteria

Each transition should reduce ambiguity and make the expected behavior
increasingly verifiable.

The specification should not silently introduce requirements that are not
supported by the established intent or requirements.

---

## 7. Requirements quality

Before implementation, relevant requirements should be evaluated for:

### Correctness

The requirement represents the intended need.

### Completeness

Necessary information is present for the intended scope.

### Consistency

The requirement does not conflict with other applicable requirements.

### Unambiguity

The requirement has a sufficiently clear interpretation.

### Feasibility

The requirement can reasonably be implemented within known constraints.

### Verifiability

Compliance can be demonstrated through an appropriate verification method.

### Traceability

The requirement can be related to its source and downstream artifacts when
traceability is required.

---

## 8. Clarification

Ptilon explicitly includes clarification before implementation when
requirements contain uncertainty.

Clarification should address, when relevant:

- ambiguous terminology;
- missing acceptance conditions;
- conflicting requirements;
- hidden assumptions;
- dependencies;
- constraints;
- exceptional behavior;
- security considerations;
- quality attributes.

Unresolved ambiguity should not be silently converted into implementation
assumptions.

---

## 9. Acceptance criteria

Acceptance criteria should make expected outcomes objectively assessable.

Good acceptance criteria should describe observable conditions rather than
prescribing unnecessary implementation details.

They should cover, where relevant:

- normal behavior;
- alternative flows;
- boundary conditions;
- error handling;
- security behavior;
- quality attributes;
- integration behavior.

---

## 10. AI-assisted requirements engineering

AI may assist with:

- elicitation preparation;
- requirement decomposition;
- ambiguity detection;
- consistency analysis;
- acceptance criteria drafting;
- traceability analysis;
- requirements review.

AI-generated requirements must be reviewed by a responsible human.

Particular attention should be given to:

- invented requirements;
- unsupported assumptions;
- missing constraints;
- over-specification;
- ambiguous language;
- contradictory requirements;
- omitted non-functional requirements.

AI should help expose uncertainty, not conceal it.

---

## 11. Requirements traceability

Ptilon promotes traceability across the requirements lifecycle.

A typical chain is:

Stakeholder Intent → Requirement → Specification → Acceptance Criteria →
Task → Implementation → Test → Evidence

Not every project requires a complete one-to-one traceability matrix. The
required level should be proportional to risk, complexity, and compliance
obligations.

---

## 12. Requirements change management

Requirements are subject to controlled change.

When a requirement changes, the project should assess its impact on:

- specifications;
- architecture;
- tasks;
- implementation;
- tests;
- security;
- quality attributes;
- documentation;
- release scope.

The source requirement should be updated before downstream artifacts are
changed.

## 13. Relationship with Spec Kit

GitHub Spec Kit provides the primary operational reference for
Specification-Driven Development in Ptilon.

The relationship is:

29148 → requirements engineering principles

Ptilon → integrated methodology and governance

Spec Kit → operational specification workflow

Ptilon uses Spec Kit without treating its commands or artifact structure as a
substitute for requirements engineering discipline.

Reference: <https://github.com/github/spec-kit>

---

## 14. Quality and security requirements

Requirements engineering must cover more than functional behavior.

Ptilon therefore expects relevant projects to consider:

- performance;
- reliability;
- security;
- usability;
- maintainability;
- compatibility;
- scalability;
- observability;
- regulatory constraints;
- operational requirements.

ISO/IEC 25010 provides the primary product quality reference within Ptilon.

NIST SSDF provides the primary secure development reference.

---

## 15. Conformance

Using ISO/IEC/IEEE 29148 as a reference does not by itself establish
conformance.

A formal conformance claim requires identification of the applicable edition,
applicable requirements, implementation evidence, and an appropriate
assessment process.

Project documentation must distinguish between:

- reference use;
- adopted practice;
- contractual requirement;
- formal conformance.

---

## 16. Ptilon implications

The 29148 reference establishes several principles for Ptilon:

1. requirements are engineering artifacts, not informal descriptions;
2. ambiguity should be resolved before it becomes implementation behavior;
3. requirements should be verifiable;
4. quality and security requirements must be considered explicitly;
5. changes should propagate from the source of truth;
6. AI-generated requirements require human validation;
7. traceability should support impact analysis and verification.
