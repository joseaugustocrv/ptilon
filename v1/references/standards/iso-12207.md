# ISO/IEC/IEEE 12207 — Software Life Cycle Processes

## 1. Purpose

Document how ISO/IEC/IEEE 12207 is used as a reference within Ptilon for
structuring and governing software life cycle activities.

This document is a Ptilon interpretation and does not reproduce the standard.

---

## 2. Reference

**ISO/IEC/IEEE 12207 — Systems and software engineering — Software life cycle
processes**

Official reference: <https://www.iso.org/standard/63712.html>

The applicable edition should be explicitly identified by projects when a
contractual, regulatory, or formal conformance requirement exists.

---

## 3. Role in Ptilon

ISO/IEC/IEEE 12207 provides the lifecycle foundation for Ptilon.

Ptilon uses it to ensure that AI-assisted development does not focus
exclusively on code generation and implementation while neglecting other
lifecycle activities.

The standard provides the lifecycle perspective; Ptilon adds its specific
approach to specification-driven development, AI assistance, traceability,
quality, security, and governance.

---

## 4. Lifecycle coverage

Ptilon uses the lifecycle perspective to ensure appropriate consideration of:

- agreement and acquisition activities;
- organizational and project enablement;
- technical management;
- technical processes;
- development;
- operation;
- maintenance;
- disposal or retirement when applicable.

The exact process set and depth of application should be adapted to the
project's context.

---

## 5. Relationship with Ptilon

The relationship can be summarized as:

ISO/IEC/IEEE 12207 → lifecycle foundation

Ptilon → integrated AI-assisted engineering methodology

Project → context-specific implementation

Ptilon does not attempt to replace the lifecycle model defined by the
standard.

Instead, it operationalizes relevant lifecycle concerns through its own
workflow and controls.

---

## 6. Mapping to the Ptilon workflow

The Ptilon workflow provides a practical engineering path across relevant
lifecycle activities:

| Ptilon activity | Lifecycle contribution |
| --- | --- |
| Constitution | Governance, organizational constraints, principles |
| Specify | Requirements and intended behavior |
| Clarify | Requirements analysis and resolution of ambiguity |
| Plan | Technical and implementation planning |
| Checklist | Readiness and quality control |
| Tasks | Work decomposition and management |
| Analyze | Consistency, impact, risk, and dependency analysis |
| Implement | Construction and integration |
| Converge | Verification, correction, and completion |
| Review | Quality, security, and acceptance review |
| Release | Controlled transition and delivery |
| Evolution | Maintenance and change management |

This mapping is conceptual rather than a claim that each Ptilon activity
corresponds one-to-one with a 12207 process.

---

## 7. AI-assisted development

AI can participate in multiple lifecycle activities, including:

- requirements analysis;
- specification drafting;
- architecture support;
- implementation;
- test generation;
- documentation;
- review support;
- maintenance analysis.

Human responsibility remains necessary for lifecycle decisions, approvals, risk
acceptance, and validation.

The use of AI therefore changes the execution model without eliminating
lifecycle responsibilities.

---

## 8. Traceability

12207's lifecycle perspective reinforces the need to maintain relationships
between lifecycle outputs.

Ptilon operationalizes this through:

Intent → Requirements → Specification → Architecture → Tasks →
Implementation → Tests → Evidence → Release

The level of traceability should be proportional to project risk and
complexity.

---

## 9. Quality and security

Lifecycle activities should incorporate quality and security concerns rather
than treating them as independent final-stage activities.

Ptilon therefore integrates:

- ISO/IEC 25010 for product quality;
- ISO/IEC/IEEE 29148 for requirements engineering;
- ISO/IEC/IEEE 42010 for architecture description;
- NIST SSDF for secure software development.

These references complement the lifecycle foundation provided by 12207.

---

## 10. Applicability

The degree of lifecycle rigor should consider:

- system criticality;
- business impact;
- security and privacy risks;
- regulatory requirements;
- contractual obligations;
- system complexity;
- organizational context;
- expected lifetime;
- operational consequences of failure.

Ptilon favors proportional application rather than identical process overhead
for every project.

---

## 11. Conformance

Using Ptilon or referencing ISO/IEC/IEEE 12207 does not by itself establish
conformance to the standard.

A formal conformance claim requires:

- identification of the applicable edition;
- determination of applicable processes and requirements;
- implementation of the required practices;
- appropriate evidence;
- assessment against the applicable conformance criteria.

Project documentation must distinguish between **using the standard as a
reference** and **claiming conformance**.

---

## 12. Ptilon implications

The 12207 reference establishes several principles for Ptilon:

1. software development is a lifecycle, not only an implementation activity;
2. lifecycle responsibilities must remain explicit when AI is used;
3. development activities should be connected to operational and evolutionary
   concerns;
4. quality and security must be integrated into lifecycle activities;
5. evidence and traceability should support important lifecycle decisions;
6. process rigor should be proportional to context and risk.
